💬 **Question**: How would I architect a RAG system for performance and reliability?

---

⭐️ **Answer**: I would optimize RAG by treating it as a complete retrieval pipeline, not simply as a database lookup. The main goal is to retrieve the smallest amount of highly relevant context, quickly and reliably.

- **Ingestion:** I would extract documents, clean the text, preserve useful metadata, and split content into meaningful chunks. Chunk size and overlap should be tested against the document structure rather than chosen arbitrarily.
- **Indexing:** I would generate embeddings with a versioned model and store both vectors and metadata. I would create indexes appropriate for the database and use metadata filters such as tenant, permissions, document type, and date before or during vector search.
- **Retrieval:** I would use hybrid retrieval—keyword search combined with vector similarity—because exact terms, identifiers, and semantic meaning are complementary. I would retrieve a relatively small candidate set, then apply a reranker to select the most relevant passages.
- **Generation:** I would send only the top, non-duplicated chunks to the language model, with a clear prompt requiring it to answer from the supplied context and say when the context is insufficient. I would include citations so the answer can be verified.
- **Performance:** I would cache embeddings and repeated queries, batch ingestion, use asynchronous I/O for independent retrieval calls, limit token usage, and stream the response when appropriate. I would also set timeouts and use graceful fallbacks if one component is unavailable.
- **Reliability and security:** I would keep ingestion separate from online querying, version documents and embedding models, apply access control before retrieval, and ensure deleted or updated documents are removed from the index.
- **Evaluation:** I would create a representative evaluation set and measure retrieval recall, precision, reranking quality, answer faithfulness, latency, and cost. I would monitor these metrics in production and use feedback to tune chunking, filters, `top_k`, and the reranker.

The architecture I would typically use is: an ingestion worker writes processed documents and embeddings to the vector store; an API receives a question; a query service applies authorization and filters; hybrid retrieval and reranking select the context; and a generation service produces a cited answer. I would keep each stage behind an interface so I can replace the vector database, embedding model, or LLM without changing the business logic. This gives me a RAG system that is accurate, observable, maintainable, and performant rather than one that only works in a demo.

- The backend creates a job record in a shared database with:
  - `job_id`
  - file location
  - status such as `PENDING`, `PROCESSING`, `COMPLETED`, or `FAILED`
  - progress percentage or processing stage
  - timestamps
  - error information
- The backend publishes a message containing the `job_id` to a durable queue such as RabbitMQ, Azure Service Bus, or AWS SQS.
- A Python worker consumes the message, downloads the file, validates it, and runs the AI pipeline.
- The worker updates the job status in the database at meaningful checkpoints—for example, uploaded, extracting, processing, and completed. If it fails, it stores a sanitized error message and marks the job as `FAILED`.
- The worker must acknowledge the queue message only after the status update and processing result are safely persisted. If the worker crashes before acknowledgment, the broker can redeliver the message.
- I would make processing **idempotent**, using the `job_id` as an idempotency key, so retries do not duplicate results.

A simpler alternative is polling `GET /jobs/{job_id}` every few seconds, which may be sufficient initially. In either case, the database preserves the state independently of the user session.

I would also include:

- **Authentication and authorization** so users can access only their own jobs.
- File-size, MIME-type, and content validation before processing.
- Object-storage lifecycle policies and encryption.
- Retry policies with exponential backoff for transient errors.

- `GET /jobs/{job_id}/result` → return the completed result

The key design principle is that **the queue triggers work, the Python worker performs it, the database stores durable state, and SignalR or polling exposes that state to the frontend**.     left, top, right, bottom = box
    return ((left + right) / 2, (top + bottom) / 2)

    for item in ocr_items:
        text_box = item["box"]
